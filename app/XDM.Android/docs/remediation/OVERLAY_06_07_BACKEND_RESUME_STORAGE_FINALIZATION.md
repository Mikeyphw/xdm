# Master remediation phases 06 + 07

Base: commit `5c64cc6c` after the request-security / queue-runtime ownership overlay.

## Phase 06 contract

Backend migration is a durable ownership transfer, not a delete-and-recreate shortcut. One nonterminal migration may own a download at a time. The exact encrypted request handoff is reconstructed and revalidated before the source is changed. Source task metadata remains recoverable through target task creation, ownership attachment and durable task persistence; only then may final source retirement remove the old mapping.

Native resume accepts partial bytes only when the checkpoint proves the same request/effective representation, a strong range validator, the exact segment graph and SHA-256 digests for persisted completed ranges. Weak or historical checkpoint evidence is not upgraded optimistically. Selective repair additionally requires the app request-security boundary and trusted block evidence. A verified backup of the original artifact remains durable until an atomic repaired-target replacement is proven; unsupported atomic replacement fails closed.

aria2 mappings are generation/install-bound and terminal states cannot be rewritten back to active/paused states. Migration retirement preserves the source GID until the target is proven. Runtime lease and ownership sidecars use crash-safe atomic replacement.

## Phase 07 contract

`destinationUri` remains the requested destination specification. A successful completion records a separate generation-bound committed artifact (`completedArtifactUri`, generation and byte count), and completed-file consumers must use that identity rather than reconstructing a path from the destination specification. Content providers must expose a provable committed size (query metadata or descriptor stat size) before XDM accepts or grants the completion; Completed terminal events carry the committed artifact rather than the destination specification.

Provider publication fails closed when atomic replacement cannot be guaranteed. MediaStore uses a fresh pending row and publishes it only after the new bytes are complete. Capacity planning includes the additional provider-copy requirement. Storage publication keeps its fsynced local `.finalization.json` evidence after destination commit instead of deleting it at backend return. Filesystem and provider writers record the exact intended/created target before the destructive commit/copy step. Startup imports surviving publication evidence into Room if process death happens before the runtime can do so; a crash after an atomic filesystem move but before the journal's final boundary is recovered from the exact committed target and byte count rather than from a now-missing staging path. The local publication journal is removed only after Room finalization is terminal. Finalization ownership is journaled with the actual attempt generation immediately when a backend reports a committed artifact, before checksum verification begins. The Room row enters Verifying before that work; pause/cancel requests during the committed-but-unverified window preserve the artifact as RecoveryRequired rather than falsely relabeling it Paused/Cancelled. Once checksum verification and generation-bound `Completed` metadata are durable, later journal-close or backend-cleanup failures do not rewrite that artifact truth; startup can close an incomplete journal from matching durable completion metadata while backend cleanup remains independently reconcilable.

Notification deep links are consumed only on a fresh launch or a newly delivered intent. Recovery actions dispatch by typed recommendation; actions that still require explicit user-selected/trusted evidence stay in RecoveryRequired instead of generically requeueing. Startup recovery reconciles scanner-owned records and removes only scanner records whose underlying condition disappeared after a complete successful scan; unresolved warnings require explicit confirmation before manual dismissal.

Saved document-provider destinations are revalidated against the live provider before they are offered or selected, backend preparation uses the centralized `DestinationProvider.canWrite` contract, and Storage Doctor probes the actually selected destination type instead of silently substituting Direct Downloads.
